Revisão do Notebook de Ingestão - Problemas Encontrados

Identifiquei 13 problemas críticos e importantes que precisam ser corrigidos antes de subir para produção:

🔴 PROBLEMAS CRÍTICOS (bloquear produção)

1. Location DBFS com mount point não configurado

  • Célula 3: LOCATION 'dbfs:/mnt/bronze/aneel' assume que o mount existe
  • Risco: Falha total se o mount não existir
  • Correção: Remover a cláusula LOCATION (Unity Catalog cria managed location automaticamente) ou usar UC Volumes

2. Escrita em /dbfs no fallback

  • Célula 4: urllib.request.urlretrieve(URL_PARQUET, f"/dbfs{temp_path}")
  • Risco: Não funciona em serverless compute; pode falhar em shared clusters
  • Correção: Usar Volume UC ou trocar por requests + spark.read.format("parquet").load(BytesIO(...))

3. Mode overwrite sem validações

  • Célula 4: .mode("overwrite") apaga dados sem verificar se a nova ingestão foi bem-sucedida
  • Risco: Perda de dados em caso de falha parcial
  • Correção: Usar tabela staging + validação + rename atômico, ou implementar merge

4. Timezone não especificado

  • Célula 4: datetime.now() usa timezone do servidor (inconsistente)
  • Risco: Timestamps incorretos; problemas em auditorias
  • Correção: datetime.now(timezone.utc) ou datetime.now(ZoneInfo("America/Sao_Paulo"))

5. URL hardcoded e frágil

  • Célula 2: URL com ano interpolado pode quebrar se ANEEL mudar estrutura
  • Risco: Falha silenciosa; difícil de debugar
  • Correção: Parametrizar via widget; adicionar validação HTTP (status 200) antes de ler

⚠️ PROBLEMAS IMPORTANTES (corrigir antes de produção)

6. Falta de parâmetros configuráveis

  • Não usa widgets do Databricks para ANO_REFERENCIA, CATALOG, SCHEMA
  • Correção: Adicionar dbutils.widgets.text() para permitir execução em diferentes ambientes

7. Logging inadequado

  • Usa print() ao invés de logging estruturado
  • Correção: Implementar logging com níveis (INFO, ERROR) e contexto JSON

8. Tratamento de erros genérico

  • Célula 4: Try/except captura qualquer exceção sem distinguir tipo
  • Célula 5: Try/except oculta erros de schema
  • Correção: Capturar exceções específicas; logar stacktrace; falhar explicitamente

9. Validações insuficientes

  • Não verifica: Dados duplicados Valores nulos em colunas críticas (distribuidora, data) Ranges de datas esperados Se o número de registros está dentro do esperado
  • Correção: Adicionar Great Expectations ou validações SQL explícitas com thresholds

10. Display() em código de produção

  • Célula 5: .display() não funciona em jobs agendados (gera erro)
  • Correção: Substituir por .show() ou logging

11. Sem idempotência

  • Executar duas vezes no mesmo dia sobrescreve dados sem controle
  • Correção: Adicionar coluna _batch_id ou usar _data_ingestao para particionar

12. Célula de exploração em notebook de produção

  • Célula 6: Consulta ad-hoc não deveria estar em código de produção
  • Correção: Remover ou mover para notebook separado de análise

13. Sem estratégia de retry e notificação

  • Falhas não disparam alertas
  • Sem retry automático em caso de falhas transientes (network timeout)
  • Correção: Implementar retry com backoff exponencial; adicionar notificação (email/Slack) via job alerts

📋 RECOMENDAÇÕES ADICIONAIS

  • Secrets: Preparar para autenticação futura (não hardcodar credenciais)
  • Versionamento: Adicionar versionamento de schema Delta (.option("delta.columnMapping.mode", "name"))
  • Particionamento: Considerar particionar por _ano_referencia para performance
  • Documentação: Adicionar TBLPROPERTIES com owner, SLA, data_source
  • Testes: Criar notebook de testes unitários separado
  • Configuração externa: Mover configs para arquivo YAML externo (já existe config.yaml no projeto)

Prioridade de correção: Itens 1-5 são bloqueadores. Itens 6-13 devem ser corrigidos antes do primeiro deploy em produção.
